# M01 — Final CTO Gate Review: Conversation Engine (Adversarial)

**Date:** 2026-08-04
**Reviewer:** CTO / Lead Architect, wearing the Google Staff Engineer hat
**Subject:** `docs/cto/m1-conversation-engine-design.md` (v1)
**Assumption:** The architecture is already deployed to **100,000 users**. Two deployment
topologies are considered, and the review is valid for the worst of the two:

- **T1 — local-first (default):** one engine instance per user device. Correctness under
  long-running per-user usage, restarts, and concurrency is the bar.
- **T2 — centralized:** many users and many workers per deployment. Adds multi-worker,
  multi-tenant, and write-throughput bars.

**Verdict: APPROVED — production-deployable — but only with the amendments below, which are
mandatory M1 scope.** The original design had 9 HIGH-severity flaws, including two
self-contradictions that would have caused data loss or double-execution of destructive
tools in production. None survive the amendments. Residual risks are documented and accepted.

**Review method:** adversarial walkthrough per area (concurrency, memory, recovery, database,
streaming, context assembly, summarization, tool routing, long conversations, large tool
outputs, cancellation, network failures, duplicate requests, crash recovery, horizontal
scaling). Each finding is traced to a concrete failure scenario at 100k users, then fixed by
amendment (A1…A22). The amended architecture is specified here; the design doc v1 has been
updated to match (see `m1-conversation-engine-design.md`, amended).

---

## 1. Findings

Legend: H = data loss / wrong side effects / security / unrecoverable; M = degraded behavior,
partial correctness; L = ops friction. `→ A#` = fix amendment.

### 1.1 Concurrency

| # | Sev | Weakness (failure scenario at 100k users) | Fix |
|---|---|---|---|
| C1 | **H** | The per-session `asyncio.Lock` exists **only in-process**. With 2+ uvicorn workers (T2), two workers serve the same session concurrently: both turns stream, both commit; `UNIQUE(session_id, seq)` catches the commit, but the user already saw two assistant replies, and tools may have run twice. The "409, never queue" guarantee is process-local. | **A1 — DB-backed turn lease.** `session_turn_lease` claimed in the same transaction as the turn's first write (`BEGIN IMMEDIATE`, INSERT with PK = session_id). Conflict → 409 across all workers. In-process lock becomes a fast-path cache of the lease, never a substitute. Lease TTL ≥ 2× max turn timeout (default 600 s), renewed by a per-turn heartbeat task; takeover allowed only after expiry (fenced by unique PK + transaction). |
| C2 | **M** | `generation` is read-modify-write in app code; under concurrent commits (A1 fix, multi-worker) two workers bump from the same base → lost update → stale caches silently serve stale history. | **A2 — generation bumped atomically in SQL** (`generation = generation + 1`) inside the same UoW transaction; caches keyed `(owner, session, generation)` + TTL as second guard. |
| C3 | **M** | LRU cap (512 live sessions) is arbitrary and can evict a session with an **in-flight turn** → lock object destroyed mid-turn. | **A3 — in-use reference counting.** Eviction never touches a session with an active turn or a lease; cap becomes a memory budget (config), eviction order = LRU among idle sessions. |
| C4 | **M** | Sync in-process event bus: a slow handler (logging/telemetry at 100k events) **blocks the event loop mid-turn**. | **A4 — bus policy + outbox.** Handlers must complete < 1 ms (contract test + benchmark); all durable fan-out (memory hooks, telemetry, future consumers) goes through `event_outbox` rows committed in the same UoW, consumed by dedicated tasks. |
| C5 | **L** | Reader pool of 2 threads undersized for T2 read amplification; fixed size in v1. | A5 — configurable pool sized by metric (reader saturation < 50%); cache-hit ratio tracked. |

### 1.2 Memory (process memory and data volume)

| # | Sev | Weakness | Fix |
|---|---|---|---|
| M1 | **H** | `messages` grows unboundedly (100k users × long conversations). Context queries stay bounded, but the DB balloons, backups slow, and `GET /conversations/{id}` returns the **entire** history — a 10k-message payload per render. | **A6 — archival compaction + pagination.** Folded messages (older than the summary watermark and ≥ N archived summaries old) move to `messages_archive` (same schema + `archived_at`) by the maintenance job; UI loads messages via `?before_seq=&limit=` (default 100), older pages read archive. No data loss; owner visibility preserved. |
| M2 | **M** | `tool_result_json` stores raw structured results unbounded (1 MB file read → 1 MB row; search → 500 items). | **A7 — storage cap** `tool_result_storage_bytes` (default 64 KB, truncate + `[truncated]`); digest cap (512 tok) already bounds context. |
| M3 | **M** | `HistoryCache` entry size unbounded (full window + margin per session); 512 sessions × 1k messages can exceed a sane RSS budget. | A8 — per-entry cap (window + margin), global memory budget, cache is advisory only (miss → repository). |
| M4 | **L** | `session_state` allows arbitrary keys → unbounded growth if misused. | A9 — engine-side key whitelist (`pending_action`, `last_filename`); repository rejects unknown keys. |

### 1.3 Recovery

| # | Sev | Weakness | Fix |
|---|---|---|---|
| R1 | **H** | **Self-contradiction.** v1 says "same `client_turn_id` retry re-runs cleanly" while `messages` has `UNIQUE(client_turn_id)`. Retry after a mid-turn crash tries to INSERT a second user message row with the same turn id → constraint violation → 500, user stuck. | **A10 — retry = reuse, not insert.** Turn protocol: (1) dedup lookup; (2) if a user-message row exists for this turn: prompt must match (else 409), row status → `processing`, **UPDATE**, no new insert; (3) dedup row INSERT is the **first** DB write of every turn (unique PK → concurrent duplicates lose at the DB, one winner); (4) statuses drive semantics: `complete` → replay terminal line, no side effects; `processing/interrupted/failed` → reuse + re-run. |
| R2 | **H** | **Tool effects are not exactly-once.** Crash between tool execution and `session_state` clear → restart restores the pending action → the user's "yes" executes the destructive tool **a second time** (e.g., delete). Retry storms after an outage amplify this across 100k users. | **A11 — `tool_executions` ledger.** Every tool execution is recorded in the same UoW: `(turn_id, seq, tool, action, args_hash, status, result_json, executed_at)`. Pending action stores `execution_ref` (turn_id+seq). On retry of an interrupted/failed turn, already-executed calls are **replayed from the ledger** (no re-execution); only unexecuted calls run. Exactly-once within the retry window; outside it, tools are either idempotent or fail benignly ("file not found"). |
| R3 | **M** | Startup `integrity_check` is O(DB) — minutes on a grown DB; interrupted-scan `SELECT` over all messages. | **A12 — `PRAGMA quick_check` + index `(status, created_at)`** for the recovery scan; batch UPDATE in one transaction; logged counts. |
| R4 | **L** | Recovery interrupted mid-recovery (crash loop) must not double-mark or corrupt. | A13 — recovery is UPDATE-only and idempotent (re-running is a no-op). |

### 1.4 Database

| # | Sev | Weakness | Fix |
|---|---|---|---|
| D1 | **H** | SQLite **single-writer** caps the engine at ~2k committed turns/min. T2 at 100k users with even 3% of users active per minute → 3,000 writes/min peak on one writer connection → `SQLITE_BUSY` storms, 503s. The v1 "100× headroom" claim is true for **one user**, not for 100k. | **A14 — shard-aware repository.** Port gains `shard(owner_id) -> shard_id = hash(owner) mod shard_count`; UoW binds to a shard. SQLite adapter = one DB file per shard (`data/db/<shard>/falso.db`, own WAL); Postgres adapter (partitioned by shard) later. Default `shard_count=1` for T1; T2 scales by shard count — capacity ≈ shard_count × 2k writes/min. No engine logic changes: every query is already owner-scoped, which makes sharding a pure adapter concern. |
| D2 | **M** | `SQLITE_BUSY` under writer contention surfaced immediately as 503. | A15 — adapter retry on busy (3×, exponential backoff + jitter) before `PersistenceError`. |
| D3 | **M** | WAL growth under heavy writes → slow checkpoints, disk bloat. | A16 — maintenance job: `wal_checkpoint(TRUNCATE)` + `PRAGMA optimize` on a schedule; `wal_autocheckpoint` tuned. |
| D4 | **L** | `PRAGMA foreign_keys`/`busy_timeout` must be set per connection — pooled connections are a footgun. | A17 — connection factory applies pragmas; conformance test asserts per-connection state. |

### 1.5 Streaming

| # | Sev | Weakness | Fix |
|---|---|---|---|
| S1 | **H** | **No bound on in-flight LLM calls.** 100k users → unbounded queue inside Ollama; queueing + 300 s timeouts = compound latency, and retries pile on. Engine has no backpressure of its own. | **A18 — provider concurrency + priority.** `LLMProvider` adapter bounds concurrent streams per model (default 4, config = Ollama concurrency), max queue depth (default 32) → typed `LLMQueueFullError` → HTTP 429 with `Retry-After` (client-side retry, already safe via A10/A11). Turns have higher priority than summarization; if saturated for `summarization_skip_seconds`, summarization is skipped (verbatim fallback) — a user turn is never degraded for a summary. |
| S2 | **M** | Client disconnect during a long tool execution: tool is atomic and non-cancellable; v1 would lose the effect's record. | A19 — cancellation order: let the in-flight tool complete, **ledger + persist its result**, then mark the turn `interrupted` and release. Effect and record are never lost. |
| S3 | **L** | Long streams killed by proxy idle timeouts; no keepalive. | A20 — configurable SSE keepalive (comment line, default 15 s). |
| S4 | **L** | 100k concurrent streams on one process → per-process streaming connection budget (409/503 beyond it); per-IP limits belong to the security middleware (tracked, M1 note). | A20b — config `max_concurrent_streams_per_process`. |

### 1.6 Context assembly

| # | Sev | Weakness | Fix |
|---|---|---|---|
| CA1 | **H** | Tool rows assemble **independently**: a `tool_call` may fit the budget while its `tool_result` does not → the model sees a call with no result (hallucinates an outcome) or a result with no call. Semantically broken turns. | **A21 — atomic pair assembly.** `tool_call` + its `tool_result` are one unit: both included or both dropped (drop the pair, newest-first, as one unit). |
| CA2 | **H** | Single summary + fixed keep-window: in a genuinely long conversation (history ≫ budget), assembly truncates the **verbatim tail** itself → the model loses the *most recent* context, the opposite of what a memory system is for. | **A22 — multi-level compression.** `minimum_verbatim_tail` (default 4) is a hard floor never dropped. When projected assembly would drop below the floor, trigger **extended summarization**: fold a larger prefix (including part of the window) into a new summary with a larger token budget (scales with folded size, capped, e.g. ≤ 4096); summaries chain via the watermark; floor always preserved. |
| CA3 | **M** | Summary text is privileged by position; an injected summary (poisoned via user text) steers the model. | A23 — summary emitted inside markers + the same "untrusted data" system directive; summaries never contain tool results (v1 D7, kept). |
| CA4 | **L** | Newest-first selection then reverse — ordering bug if applied inconsistently. | A24 — assembly contract: select newest-first, emit oldest-first, chronological within pairs; property test. |

### 1.7 Summarization

| # | Sev | Weakness | Fix |
|---|---|---|---|
| SU1 | **M** | Summarizer competes with user turns for the same LLM provider; no priority in v1. | A18 (priority queues, skip-on-saturation). |
| SU2 | **L** | Single global worker = single point of rate for 100k sessions. | A25 — configurable workers (default 1), per-session FIFO ordering preserved (watermark + `UNIQUE(session_id, base_message_id)`). |

### 1.8 Tool routing

| # | Sev | Weakness | Fix |
|---|---|---|---|
| TR1 | **H** | Pending-action crash window + retry double-execution of destructive tools. | A11 (ledger) + pending stores `execution_ref`; TTL honored on restore. |
| TR2 | **M** | Offline property: tool-only turns must never depend on LLM health. | A26 — routing path never checks provider health; tool-only turns proceed when the LLM is down (test enforced). |

### 1.9 Long conversations

| # | Sev | Weakness | Fix |
|---|---|---|---|
| LC1 | **H** | Unbounded `GET /conversations/{id}` payload (M1) and unbounded DB growth. | A6 (archive + pagination). |
| LC2 | **M** | Assembly degrades smoothly with length. | A22 (multi-level compression). |
| LC3 | **L** | Summaries chain correctness under rapid turns. | A27 — fuzz/property tests on watermark chains (no gaps, no duplicates, monotonic seq). |

### 1.10 Large tool outputs

| # | Sev | Weakness | Fix |
|---|---|---|---|
| LO1 | **M** | Stored raw results unbounded (M2). | A7 (storage cap). |
| LO2 | **L** | Digest cap truncation without signal to the model. | A28 — `[truncated]` marker already in v1; ensure it survives assembly truncation too (A21 pair drops preserve it). |

### 1.11 Cancellation

| # | Sev | Weakness | Fix |
|---|---|---|---|
| X1 | **M** | Cancel ordering unspecified between persistence, LLM teardown, and lease release. | A29 — defined order: persist partial (`interrupted`) → commit → `aclose()` LLM stream → release lease → emit `TurnInterrupted`. Never release before persist (else a second worker could take over mid-commit). |
| X2 | **L** | Cancel of the client ≠ cancel of summarization. | A30 — summarizer unaffected by client state (idempotent, watermark). |

### 1.12 Network failures

| # | Sev | Weakness | Fix |
|---|---|---|---|
| N1 | **M** | Ollama down → LLM turns fail (typed error, `interrupted`) — v1 OK — but retry storms re-queue unboundedly. | A18 (provider queue + 429) + A31 — 503 responses carry `Retry-After`; client backoff contract documented. |
| N2 | **L** | No distinction between "client gone" and "server error" in stream terminal lines. | A32 — wire contract adds `{"type":"error","code":…}` codes; `interrupted` vs `failed` semantics documented. |

### 1.13 Duplicate requests

| # | Sev | Weakness | Fix |
|---|---|---|---|
| DU1 | **H** | Dedup race window: if two identical requests arrive concurrently, both may pass the lookup before either inserts. | A10 (dedup INSERT is the first write; PK uniqueness arbitrates; loser → 409). |
| DU2 | **M** | Same turn id, different prompt = client bug → silent wrong behavior. | A33 — prompt mismatch on reuse → 409 (id is a turn identity, not an ID for arbitrary content). |

### 1.14 Crash recovery

| # | Sev | Weakness | Fix |
|---|---|---|---|
| CR1 | **M** | Recovery scan cost + index (R3). | A12. |
| CR2 | **M** | A crash after the user message commit but before `session_state` restore means runtime state must be fully rehydratable from DB — v1 yes, but pending `execution_ref` (A11) must also survive. | A34 — `session_state` schema versioned (add `schema` field); rehydration contract tested. |
| CR3 | **L** | Expired leases/dedup rows accumulate. | A35 — maintenance job purges (dedup TTL 24 h, leases at expiry + margin). |

### 1.15 Horizontal scaling

| # | Sev | Weakness | Fix |
|---|---|---|---|
| HS1 | **H** | Multi-worker correctness requires the lease (C1), outbox (C4), sharding (D1), atomic generation (C2) — none in v1. | A1/A2/A4/A14 — all are adapter-level or protocol-level; the domain layer changes only in the turn protocol (A10). Multi-worker story: N workers, same shard set, session affinity recommended (cheap wins) but **not required** — the lease makes it correct without it. |
| HS2 | **M** | Cross-worker cache coherence: generation-keyed caches are consistent-by-miss; add TTL as second guard. | A36 — cache entry TTL (default 30 s) + generation key. |
| HS3 | **L** | In-process bus cannot fan out across workers. | A4 (outbox) — consumers read the outbox with a worker id; a broker adapter later replaces the outbox reader, not the domain. |

## 2. Amended architecture (delta specification)

The amendments change five things structurally: the **turn protocol**, the **schema**,
three **ports**, the **assembly algorithm**, and the **maintenance job**. Everything else in
v1 is unchanged and remains valid.

### 2.1 Turn protocol (supersedes v1 §4.1/§12)

```
Turn(session_id, owner, prompt, client_turn_id):
 1. dedup = SELECT turn_dedup WHERE turn_id = client_turn_id          (owner-scoped)
 2. if dedup.status == complete:    → replay stored terminal line, NO side effects
 3. if dedup exists and user-message row exists for turn:
       prompt != stored content  → 409
       else → reuse row (status→processing, UPDATE)
    else: new user message row
 4. UoW begin (shard of owner):
      INSERT turn_dedup (PK conflict → concurrent duplicate → 409)   ← FIRST write
      lease: INSERT session_turn_lease (PK conflict → 409 unless expired → takeover)
      insert/reuse user message, generation += 1 (SQL atomic)
      enqueue outbox rows (TurnStarted)
 5. UoW commit
 6. heartbeat task renews lease every lease_ttl/3 while streaming
 7. assemble → route → stream; each tool execution ledgered (A11) before effects commit
 8. on terminal: append assistant (or ledger replay on retry), outbox TurnCompleted,
    UoW commit, dedup → complete, release lease, release in-process lock
 9. failure paths: interrupted (partial persisted, then A29 order) | failed (dedup=failed)
```

### 2.2 Schema additions (design-doc §7 updated)

```sql
CREATE TABLE session_turn_lease (
  session_id   TEXT PRIMARY KEY REFERENCES sessions(id) ON DELETE CASCADE,
  lease_token  TEXT NOT NULL,
  worker_id    TEXT NOT NULL,            -- hostname:pid
  acquired_at  TEXT NOT NULL,
  expires_at   TEXT NOT NULL
);
CREATE INDEX idx_lease_expiry ON session_turn_lease(expires_at);

CREATE TABLE tool_executions (
  turn_id      TEXT NOT NULL REFERENCES turn_dedup(turn_id) ON DELETE CASCADE,
  seq          INTEGER NOT NULL,         -- order within the turn
  tool         TEXT NOT NULL,
  action       TEXT NOT NULL,
  args_hash    TEXT NOT NULL,
  status       TEXT NOT NULL CHECK (status IN ('executed','failed','replayed')),
  result_json  TEXT,                     -- capped digest (A7)
  executed_at  TEXT NOT NULL,
  PRIMARY KEY (turn_id, seq)
);

CREATE TABLE event_outbox (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id   TEXT,
  owner_id     TEXT NOT NULL,
  event_type   TEXT NOT NULL,
  payload      TEXT NOT NULL,            -- JSON, versioned
  created_at   TEXT NOT NULL,
  processed_at TEXT,                     -- set by consuming worker
  CONSTRAINT fk_outbox_session FOREIGN KEY (session_id)
    REFERENCES sessions(id) ON DELETE CASCADE
);
CREATE INDEX idx_outbox_pending ON event_outbox(processed_at, created_at)
  WHERE processed_at IS NULL;

CREATE TABLE messages_archive (          -- same columns as messages
  ... ,
  archived_at TEXT NOT NULL
);

CREATE INDEX idx_messages_status ON messages(status, created_at);   -- recovery scan
```

### 2.3 Port additions (design-doc §6 updated)

```python
class TurnLeaseManager(Protocol):
    async def acquire(self, session_id, owner_id, *, ttl_s, worker_id) -> str | None
    async def renew(self, token, *, ttl_s) -> bool
    async def release(self, token) -> None

class ToolLedger(Protocol):                       # exactly-once tool effects
    async def record(self, uow, turn_id, seq, tool, action, args_hash, status, result) -> None
    async def by_turn(self, uow, turn_id) -> list[ToolExecution]

class Outbox(Protocol):                           # durable fan-out (A4)
    async def enqueue(self, uow, event) -> None
    async def claim_batch(self, worker_id, limit) -> list[OutboxRow]
    async def ack(self, row_ids) -> None

class ConversationRepository(Protocol):           # amended
    async def paginated_messages(self, uow, session_id, owner_id, *, before_seq, limit) -> list[Message]
    async def archive_messages(self, uow, session_id, up_to_seq) -> int
```

LLMProvider adapter gains bounded concurrency + priority (A18). `MemoryGateway` unchanged.
Repository port becomes shard-aware **behind the adapter** (no signature change: shard is
derived from owner inside the adapter).

### 2.4 Assembly amendments (supersedes design-doc §9.1)

- **Atomic pairs:** `tool_call`+`tool_result` = one budget unit (A21).
- **Hard floor:** `minimum_verbatim_tail` (4) never dropped (A22).
- **Extended summarization:** when floor is threatened, fold window prefix into a larger
  summary (chain via watermark, capped 4096) (A22).
- **Markers:** summary and every tool result inside explicit markers, untrusted-data
  directive applied to both (A23).

### 2.5 Maintenance job (new component, own executor, injected clock)

Runs on a schedule (`maintenance_interval_seconds`, default 300): purge expired dedup rows
and leases; WAL checkpoint + `PRAGMA optimize` per shard; archival compaction (folded
messages → `messages_archive` when ≥ `archive_after_summaries` summaries deep); outbox
dispatch to consumers. Never on the request path. Crash-safe by design (idempotent,
watermarks).

| Field | Default | Purpose |
|---|---|---|

| `lease_ttl_seconds` | `600` | ≥ 2× max turn timeout (A1) |
| `provider_max_concurrent` | `4` | per-model LLM stream bound (A18) |

## 3. What did NOT change (and why it survived)

- Hexagonal layering, ports, DI, UoW per turn — survive; UoW now also carries lease, outbox,
  ledger writes (same transaction, no extra fsync cost).
- Pure assembler with `AssemblyReport` — survives; amended algorithm only.
- NDJSON wire contract — survives; additive fields only (`conversation_id`, `turn_id`,
  `error.code`).
- Per-owner scoping everywhere — survives; it is what makes sharding a pure adapter concern.
- SQLite + WAL stack decision — survives; bounded by sharding, not replaced.
- Phase C constraints (single process default, no broker, no ORM) — survive.

## 4. Residual risks (accepted, with mitigation)

| Risk | Mitigation |
|---|---|
| Sharded SQLite: cross-shard queries (none exist in the engine — every query is owner-scoped; migration script iterates shards) | None needed; documented invariant + contract test |
| Exactly-once only within retry window; outside it, tool effects are at-least-once | Tools designed idempotent-or-benign (delete = "not found" on re-run); ledger makes the common case exactly-once |
| Lease expiry vs. long stream under extreme stall | Renewal task + TTL ≥ 2× max turn; takeover after expiry is fenced |
| Cloud LLM pooling (multi-provider) | M2 provider work; queue/priority contract is already the seam |
| Summary fidelity loss on extreme histories | Verbatim floor + summary chain + append-only provenance for M4 |

## 5. Gate decision

**APPROVED** — with the amendments above as **mandatory M1 scope** (they are specified at
the same level of detail as the rest of the design; implementation order unaffected).

Conditions tracked until the M1 tag (`v2.0-m1`):
1. A1/A10/A11 conformance tests (lease, dedup reuse, ledger replay) land with the feature.
2. Adversarial tests for CA1 (pair drops) and CA2 (floor preservation) are part of the
   assembler suite.
3. Multi-worker stress test (2 workers, same shard set, 20 concurrent sessions) in the
   integration tier.
4. `benchmarks/M01.json` includes the §18 additions (lease/ledger/outbox p95, shard write
   throughput at `shard_count` = 1 and 4).
5. Migration script verifies per-shard import when `shard_count > 1` (T2 deployments).

The reviewer would deploy this architecture to production **today** for T1 (local-first)
and to T2 at up to the shard-count ceiling, with the M2 provider pooling work as the next
latency/capacity investment. Nothing below this gate blocks the implementation milestone.
